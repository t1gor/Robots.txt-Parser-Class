# Contributing

Thank you for your interest, and for wanting to help.

Pull requests go to `master`. Please keep an eye on the following:

- A fix should come with a test that fails without it (phpUnit).
- `composer complexity` must stay green - CI fails when the total grows, which somehow does keep
  things simpler.
- Coding standard: tabs for indentation, camelCase, and match the file you are editing.
- No local PHP needed: `docker run --rm -v "$PWD":/app -w /app php:8.3-cli vendor/bin/phpunit`
  works, and any of the `php:8.2`-`php:8.5` images will do.

## Changelog

`CHANGELOG.md` is generated by [git-cliff](https://git-cliff.org) from conventional commit
subjects, so `fix(#62): what changed (#140)` becomes a `### Fixed` entry linking both the PR and
the issue it closes. Pushing a `v*` tag runs `.github/workflows/release.yml`, which writes the new
section, pushes it back to `master` and publishes the same text as the release body.

Preview before tagging - `bin/changelog.sh` uses a pinned Docker image when `git-cliff` is not on
`PATH`:

```sh
bin/changelog.sh              # unreleased section, to stdout
bin/changelog.sh --write      # ... and splice it into CHANGELOG.md
composer changelog            # same, through composer
```

Sections land directly under the `<!-- changelog-insert -->` comment. Everything below it, `0.3.0`
included, is hand-written and never regenerated.

## Performance budgets

`performance.yml` gates every change against two budgets per case, and fails the job when either
is exceeded. This records where those numbers come from, so tightening them later is a measurement
rather than a guess.

`performance.yml` fails a job when a parse runs past its `budget` (seconds). This records where
those numbers come from, so tightening them later is a measurement rather than a guess.

### How they were set

Three Performance runs per side, same code within a side, `parse_seconds` from each job's
`benchmark.json` artifact. Budget is ~1.6-2x the slowest of the three.

| case | master | this code | worst | budget |
| --- | --- | --- | --- | --- |
| 250 MB | 3.40 / 3.44 / 3.53 | 2.71 / 3.37 / 3.41 | 3.41 | 6 |
| 600 MB | 3.16 / 5.98 / 8.05 | 6.13 / 8.17 / 8.25 | 8.25 | 14 |
| 1 GB | 6.02 / 6.24 / 13.82 | 13.82 / 13.92 / 14.09 | 14.09 | 24 |
| 250 MB rules only | 24.05 / 28.42 / 28.49 | 12.60 / 13.24 / 20.50 | 20.50 | 32 |
| Few agents, 50k rules each | 3.01 / 3.08 / 3.08 | 1.38 / 2.47 / 2.50 | 2.50 | 5 |

### Why the margin is not padding

The margin absorbs the runner, not the parser. Every matrix entry is a separate job on a separate
machine, and the hosted fleet is not uniform: unchanged master parsed 600 MB at 190 MB/s on one
run and 75 MB/s on another, and 1 GB took 6.02 s and 13.82 s on runs of the same commit.
`cpu_percent` is 100 in every job and `cpu_seconds` tracks wall clock, so this is the CPU the job
was given, not disk contention - nothing about how the benchmark is measured can remove it.

So a budget set at the observed best would fail on unchanged code. These budgets catch a collapse
or a regression of roughly 1.7x and worse. They do **not** catch drift of tens of percent.

### The ratio gate

Seconds are not comparable between runs, so there is a second gate that is. `bin/benchmark.php`
times a fixed synthetic loop in the same process before it opens the file, and reports
`parse_ratio = parse_seconds / calibration_seconds`. Machine speed divides out, so this number is
comparable across runs and is the one that catches drift.

The probe deliberately **does not call the parser**. It runs the primitives the parser leans on -
`preg_match` against a short line, `explode`, `trim`, an array write - and nothing from `source/`.
That is the whole point: a probe that used the parser would slow down alongside a regression and
the ratio would never move. It takes the best of 7 rounds, because scheduling noise only ever adds
time, so the minimum is the cleanest estimate of what the CPU can do. Cost is about 1 s per job.

#### Ratio budgets

`parse_ratio` scales linearly with file size for a fixed shape (measured: 0.0320, 0.0310 and
0.0330 ratio per MB at 50, 100 and 200 MB of the same shape), so a budget can be derived per case
from the shape's ratio-per-MB. Budgets are ~1.15x the measured value.

| case | shape | ratio/MB | expected | ratio budget |
| --- | --- | --- | --- | --- |
| 250 MB | density 0.02 | 0.032 | 8.0 | 10 |
| 600 MB | density 0.02 | 0.032 | 19.2 | 24 |
| 1 GB | density 0.02 | 0.032 | 32.8 | 40 |
| 250 MB rules only | density 1, group 100 | 0.260 | 65.0 | 74 |
| Few agents, 50k rules each | density 1, group 50k | 0.271 | 7.1 | 8 |

#### How it was validated

Machine speed was varied deliberately with `docker run --cpus`, rather than waiting for the runner
lottery, and each point was measured against both this code and master.

| cpus | master s | branch s | calibration s | master ratio | branch ratio |
| --- | --- | --- | --- | --- | --- |
| 0.4 | 3.99 | 3.20 | 0.3814 | 10.2 | 8.4 |
| 0.7 | 1.90 | 1.61 | 0.2069 | 8.9 | 7.8 |
| 1.0 | 1.33 | 1.19 | 0.1558 | 8.6 | 7.6 |
| 2.0 | 1.38 | 1.10 | 0.1529 | 9.0 | 7.2 |

- **Machine-independent.** Across a 199% swing in wall clock the ratio moved 17%, and most of that
  is the 0.4-cpu point, where CFS throttling hits a long parse harder than a short probe round.
  Between 0.7 and 2.0 cpus the ratio holds inside 5-8%.
- **Still sensitive to code.** master 8.6-10.2 against 7.2-8.4 here: the ranges do not overlap, so
  the gate separates the two. End to end, at the configured budgets, this code passes and master
  fails on both rule-heavy shapes.

#### The honest limit

The win being defended is 17-20%, and the ratio's residual spread is 5-8% on a normal runner. The
budgets above therefore sit about 15% over measured - enough to catch a regression of roughly that
size, but not with much room to spare. If a case turns out to flake, the fix is not a looser budget
but a quieter measurement: raise `CALIBRATION_ROUNDS`, or parse more than once and keep the
fastest. The latter is cheap for `Few agents` and expensive for `1 GB`, which is why it is not on
by default.

Both gates stay. Wall clock catches a collapse even if the probe itself is ever wrong; the ratio
catches drift.

### Re-measuring

```sh
gh workflow run performance.yml --ref <branch>          # repeat 3x
gh run download <run-id> -D <dir>                       # benchmark.json per case
```

Take the slowest of three per case, apply the same margin, and update both the table above and the
`budget` values in `performance.yml`. For the ratio, read `parse_ratio` out of the same
`benchmark.json` - it needs no scaling between machines, which is the point of it.
